# The knowledge base: how it was built and its limits

The planner reasons over four committed JSON files in [`../data/`](../data/).
They are *curated reference data*, regenerated by
[`../scripts/build_kb.py`](../scripts/build_kb.py) and validated by
`python -m aep validate-kb`.

## Files

| File | Contents |
|---|---|
| `techniques.json` | ATT&CK techniques: `id`, `name`, `tactic`, short description, ATT&CK `data_sources`, and the common Windows/Sysmon `log_events` that carry the telemetry (e.g. Security 4688, Sysmon 1, Security 4624). |
| `actor_profiles.json` | Six threat-actor archetypes, each with a technique list. |
| `atomic_map.json` | technique -> Atomic Red Team **test identifiers** (`T1059.001-2`) and titles. IDs and titles only; no commands. |
| `detections.json` | technique -> detection ideas: Sigma rule titles, Splunk/KQL pseudo-logic, and the owner's repo that implements each. |

## How it was built

1. Techniques were selected to cover the full Enterprise kill chain (all 14
   tactics) with roughly 80–95 of the most commonly emulated techniques,
   weighted toward Windows/AD because that is what the lab telemetry covers.
2. Each technique's `data_sources` follow ATT&CK; the `log_events` are the
   concrete event IDs a defender actually queries, so the planner can map a
   technique to telemetry the environment either collects or does not.
3. The Atomic map references the public Atomic Red Team project by test
   identifier and title. The convention `T<id>-<n>` points a tester at the
   atomic to run without this repo reproducing any command.
4. Detection ideas point back to real rules in the owner's detection repos
   (`microsoft-sentinel-detection-engineering`, `splunk-threat-detection-lab`,
   `siem-from-scratch`) so planning connects to shipped work.

## Profiles

Generic names (`Group A` … `Group F`) describe *archetypes* modelled on public
reporting patterns — ransomware affiliate, state-nexus espionage, eCrime
loader/access broker, malicious insider, hacktivist, social-engineering
intrusion set. They deliberately make **no claims about specific named
real-world groups**; they are a way to select a realistic technique set.

## Limits (be honest about these)

- **It is a slice, not all of ATT&CK.** ~90 techniques out of 600+; sparse on
  macOS, Linux, cloud-control-plane and container techniques.
- **Atomic coverage is partial.** Not every technique has a mapped atomic, and
  atomic test numbering can change upstream — treat the identifiers as pointers
  to verify against the current Atomic Red Team repo, not as frozen truth.
- **Detection ideas are pseudo-logic.** The KQL/Splunk snippets are planning
  aids; the authoritative, tested rules live in the detection repos.
- **Profiles are archetypes.** They approximate behaviour classes; a real
  engagement should refine them with current, source-attributed intel.
- **No severity scoring of the actor.** The planner rates *test* risk (to the
  environment), not business risk of the actor.
